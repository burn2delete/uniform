# Gravity Implementation Roadmap

Status: active; staged bootstrap surfaces exist, but final seed retirement and
final public seedless release are incomplete

This roadmap translates the 240-document Gravity specification set into
agent-executable implementation work. It does not replace the normative
documents. Each task points workers back to the owning phase documents and
requires concrete fixtures, diagnostics, artifacts, and evidence before
progress can be marked complete.

Current validation: the latest fail-closed correction has focused P15/P18
tests proving that final seed retirement and final public seedless release are
blocked rather than complete. Full-suite validation must be rerun before any
new broad completion claim. Co-canonical `.qst` and `.gravity` source
extension support remains proven and co-canonical.

Full-language completion is tracked separately in
[`docs/full-language-implementation-gap-map.md`](full-language-implementation-gap-map.md).
That track is active and open. It records the gap between the current proven
public release surface and the complete designed Gravity language. Historical
`complete` statuses in this roadmap mean complete for the stated stage0,
stage3, compiled-app, proof, or current accepted executable release surface;
they do not mean the full designed language is implemented or fully
self-hosted.

## Product Release Truth Gate

The capability-gated staged implementation is not complete for product-level
"done". Earlier phases remain complete only for their stated stage0, stage1,
stage2, stage3, compiled app, and proof surfaces. The current P15 final
seed-retirement proof is incomplete and records
`:full-language-compiler-self-hosted? false`, `:clojure-seed-retired? false`,
and `:clojure-seed-boundary? true`. Because that proof is incomplete, P18-T06
is also incomplete: `bin/gravity` must not select the generated release
candidate as the public final release and currently falls back to the packaged
JVM CLI path.

Product-level "done" requires a Phase 18 final release proof produced after
the P15 seed boundary is genuinely retired: a public `gravity` executable
produced from the self-hosted compiler path, accepted and rejected fixtures
through that executable, stable diagnostics, reproducible binary evidence,
provenance, SBOM, signing records, release governance evidence, and a release
proof recording `:clojure-seed-boundary? false` for the binary, compiler path,
runtime path, and release compiler path.

The final aggregate completion gate is open. These checks remain required
through the self-hosted public binary before completion can be claimed:

- `gravity check examples/core-app.gravity`
- `gravity check examples/core-app.qst`
- `gravity run examples/core-app.gravity`

## Execution Protocol

- Claim one task ID at a time and keep edits scoped to that task.
- Before implementation, read `AGENTS.md`, this overview, the phase roadmap,
  the phase `README.md`, and every governing document listed by the task.
- A task is complete only when accepted behavior, rejected behavior,
  diagnostics, artifacts, and evidence are present or the task explicitly
  states why one of those outputs is not applicable.
- Update progress checkboxes in the phase roadmap only after evidence exists.
- Add a dated evidence-ledger row in the phase roadmap for every progress
  update.
- Do not claim milestone, release, safety, performance, or self-hosting
  support without the evidence bundle required by `D2`, `D8`, and `D9`.

## Task Status Legend

- `[ ]` not started or not yet evidenced
- `[x]` complete with linked evidence
- Status words in tables should use `not started`, `in progress`, `blocked`,
  `review`, or `complete`.

```text

-> L10 -> SAFE1 -> L15 -> P1 -> PERF1 -> C1 -> C18
```

from earlier phases and does not claim release status.

## Definition Of Done For Roadmap Tasks

- The task names the governing document IDs and exact source files.
- The implementation produces an accepted fixture or artifact.
- The implementation produces a rejected fixture or diagnostic where the
  governing document defines invalid behavior.
- The evidence can be reproduced by a command, test, artifact hash, or
  checked report.
- The phase roadmap status and evidence ledger are updated in the same change
  that completes the task.
