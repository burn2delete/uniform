projection, generated diagnostic-origin recovery and private candidate product
assembly into gravity.resolution. D1, D2, D3, D9, L3, C3, C4, C5, C15, BOOT8
and TEST2 govern the boundary. The stage consumes existing syntax, verified
module views and resolver results through explicit inputs and seed operations.

Public APIs are base-request, module-request, diagnostic-origin and
assemble-candidate. Outputs are unchanged request records, an exact generated
origin or nil, and private aggregate/descriptor construction data. The existing
Bootstrap owner keeps parent admission, module-artifact verification, source
snapshots, resolver execution, contextual authority, envelope admission and the
mandatory final capability-proof/publication gate. A candidate's existing
accepted status tag is not publication authority; its proof remains absent
until the existing final gate completes.

Compatibility entry points retain their existing arities. Module views are
verified before the pure module-request projection. Diagnostic origins require
the same exact reference, diagnostic facts, owner syntax and parent identity.

and private/public plan-field separation. Its operations, configuration and
stage roots must qualify receipt reuse and construction drift.

Acceptance requires real library/consumer products with actual verified module
premises, actual unresolved-reference rejection, fresh public verification and
complete before/after product and diagnostic comparisons. Focused tests cover
request composition, source/header provenance, exact origin recovery, candidate
data, proof absence and dependency drift. Independent review, clean commits,
current CI, prerequisite integration and exact main preflight remain required.

performance, self-hosting or seed-retirement authority is claimed.
